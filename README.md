# RSS Watch — Wikipedia Editor Analysis (Static Site)

A plain **HTML / CSS / JavaScript** site (no framework, no build step)
that renders the per-editor reports produced by the
`wiki.py → editor_m.py → report.py` pipeline.

Supports **multiple Wikipedia pages** — if your `editor_reports/` folder
contains reports for several different articles (e.g. "Hindu American
Foundation", "Rajiv Malhotra"), each gets its own overview, and the
landing page lets you pick which one to view.

## Pages

1. **`index.html`** — landing page: a card for every analyzed Wikipedia
   page, with aggregate stats (editors, hits, avg score). If only one
   page has been analyzed, this redirects straight to it.

2. **`page.html?page=<page_slug>`** — per-page editor overview: stats
   for that article, a card grid of every editor analyzed on it
   (sorted by score, click → profile), and that page's highest-scoring
   hits.

3. **`editor.html?page=<page_slug>&editor=<editor_slug>`** — per-editor
   profile: account info, executive summary, qualitative insight,
   revision timeline, and every flagged hit with its rebuttal,
   filterable by category.

## How it works

`scripts/sync_reports.py` reads every `*.json` file from your
`editor_reports/` folder (the output of `report.py`), groups them by
`page_title` (different reports can come from different Wikipedia
articles), normalizes **both schema versions**:

- **old** — `edit_patterns` + `narrative` / `policy_ref` (severity 1–5)
- **new** — `phobic_references` + `rebuttal` / `rebuttal_source` (score 1–8)

...into one consistent shape, and writes static JSON into:

```
data/pages.json                       <- list of all analyzed pages
data/pages/<page_slug>/index.json     <- per-page editor list + top hits
data/editors/<page_slug>__<editor_slug>.json  <- one normalized file per editor
```

Editor files are **namespaced by page** (`<page_slug>__<editor_slug>.json`)
so the same username editing two different articles doesn't collide.

In both schemas, the per-hit "rebuttal" field is shown identically in
the UI (old `narrative`/`policy_ref` is mapped onto `rebuttal`/
`rebuttal_source`), so reports generated by either version of
`report.py` render the same way.

## Usage

### 1. Place your reports

Put all `*__report.json` files (regardless of which Wikipedia page they
analyze) into an `editor_reports/` folder next to this project:

```
rss-watch-static/
├── editor_reports/        <- your report.py output goes here
│   ├── Kautilya3__report.json
│   ├── _2026-33953-78__report.json
│   └── ...
├── index.html
├── page.html
├── editor.html
└── ...
```

(`editor_reports/` is gitignored — only the generated `data/` folder is
deployed.)

### 2. Sync

```bash
python3 scripts/sync_reports.py

# Or point at a different folder:
EDITOR_REPORTS_DIR="/path/to/editor_reports" python3 scripts/sync_reports.py
```

This is read-only with respect to your reports — it only reads the
existing `*.json` files and writes into `data/`.

The script prints a summary, e.g.:

```
[OK]  [Hindu_American_Foundation] Kautilya3        score 6.25/8  (4 hits)
[OK]  [Rajiv_Malhotra]            ~2026-33953-78   score 5.0/8   (4 hits)

[PAGE] Hindu American Foundation   1 editor(s), 4 hit(s)
[PAGE] Rajiv Malhotra              1 editor(s), 4 hit(s)
```

### 3. Preview locally

Any static file server works, e.g.:

```bash
python3 -m http.server 8080
# then open http://localhost:8080
```

(Plain `file://` won't work for `fetch()` due to browser CORS rules —
use a local server.)

### 4. Deploy to Vercel

```bash
vercel deploy
```

`vercel.json` is configured for a static deployment with `cleanUrls`
(so `/page?page=...` and `/editor?page=...&editor=...` work without
the `.html` extension) and short-cache headers on `/data/*`.

To refresh the site after generating new reports: drop the new
`*__report.json` files into `editor_reports/`, re-run
`scripts/sync_reports.py`, commit the updated `data/` folder, and push
(or redeploy).

├── index.html               Landing page — list of analyzed Wikipedia pages

## Notes

- Editor slugs are derived the same way as the filenames `editor_m.py`
  already produces (`re.sub(r"[^\w\-]", "_", username)`), and page
  slugs are derived the same way from `page_title`. URLs like
  `editor.html?page=Hindu_American_Foundation&editor=Kautilya3` map
  directly to `data/editors/Hindu_American_Foundation__Kautilya3.json`.
- IP (v4 and v6) editors are detected automatically and shown with a
  distinct "IP Editor" badge/icon.
- Usernames starting with `~` (e.g. anonymized accounts like
  `~2026-33953-78`) are handled correctly — the leading `~` is stripped
  by the same slug rules `editor_m.py` uses for filenames.
- If `report.py` hasn't been re-run with the new rebuttal pipeline,
  old reports with `edit_patterns[].narrative` /
  `edit_patterns[].policy_ref` still render correctly — these are
  mapped onto the same "Rebuttal" / "Source" UI as the new
  `phobic_references[].rebuttal` / `.rebuttal_source` fields.
